# Dataset note — superseded census reason on the `NEOVERSEN2` arm

**Applies to:** run `20260820T031023Z-ip-172-31-36-19`
(`c8g.metal-48xl`, `i-04194f1208ee1d602`, `us-east-1a`, on-demand, P2 pass 1)
**File affected:** `census-20260820T031023Z-ip-172-31-36-19.ndjson`, one record
**Records affected in `bench-*.ndjson`:** none
**Written:** 2026-08-20, while the pass was still running
**Harness at time of run:** `9048a2b` — which is *before* `fda125b`

This note exists because the census of this pass carries a status and a reason
string that the current code can no longer emit for this arm, and a published
record containing an unreachable status is defensible only if the discrepancy is
documented. It is not an erratum against a measurement: no number in this dataset
changes, and no arm that ran is affected. It is an erratum against one
*explanation of an absence*.

The shipped census is **not** edited. Editing a record after it shipped is worse
than either leaving the discrepancy or re-running, because it destroys the only
evidence of what the harness actually did.

## What the record says

```json
{
  "record": "arm_outcome",
  "library": "openblas", "target": "DYNAMIC", "coretype": "NEOVERSEN2",
  "coretype_effective": "neoversev2", "threads": 0,
  "status": "unrunnable", "records": 0,
  "reason": "requested coretype NEOVERSEN2 but openblas_get_corename() reports
             neoversev2, which is not a declared alias of it; force_coretype()
             ignored the request and the arm would be an unlabelled duplicate of
             the unforced arm"
}
```

## What it should say, and does say from `fda125b` onward

```json
{
  "record": "arm_outcome",
  "library": "openblas", "target": "DYNAMIC", "coretype": "NEOVERSEN2",
  "coretype_effective": "neoversev2", "threads": 0,
  "status": "alias_duplicate", "records": 0,
  "reason": "requested NEOVERSEN2; openblas_get_corename() reports 'neoversev2',
             which the NEOVERSEV2 arm is already measuring. The two requests
             select the same kernel set -- that is the finding, and measuring it
             twice would read as two independent arms."
}
```

Same arm, same `threads=0`, same `records=0`, same single record emitted from the
same pre-flight coretype probe loop in `scripts/run-matrix.sh`. Only the status
and the reason differ.

## Why the shipped reason is wrong, not merely differently worded

The shipped reason asserts that `force_coretype()` ignored the request. It did
not. In OpenBLAS `cc3fc1e` (the SHA this pass built, recorded in
`manifest-*.ndjson`):

- `driver/others/dynamic_arm64.c` `#define`s `gotoblas_NEOVERSEV2` to
  `gotoblas_NEOVERSEN2` unconditionally — outside every `DYN_*`/`NO_SVE` branch,
  with no separate V2 table anywhere in the tree. The two names are one pointer.
- `force_coretype("NEOVERSEN2")` matches `corename[13]`, finds it, and returns
  **exactly the table that was requested**. The request *was* honoured.
- `gotoblas_corename()` then tests `corename[12]` (`"neoversev2"`) *before*
  `corename[13]` (`"neoversen2"`) against that one pointer, so in this tree it
  can never return `"neoversen2"` for any request. Both requests report
  `neoversev2`.

So the reported name differing from the requested name is the campaign's central
aliasing assumption coming true on SVE2 silicon — the *finding*, not a failure.
The `9048a2b` alias guard declared only the `NEOVERSEV2:neoversen2` direction and
this hardware takes the other one, so the check meant to *detect* the aliasing is
what suppressed it. `fda125b` declares both directions; `9667ea0` is its
follow-on and unrelated.

## What this does and does not change in the analysis

- **The measured arm set is identical.** `NEOVERSEN2` produced zero bench records
  under either status, on purpose and for the same underlying reason, so every
  GFLOP/s, efficiency figure, verdict and denominator in this dataset is
  unaffected.
- **Standing order 11 is satisfied either way.** `unrunnable` and
  `alias_duplicate` both sit outside `decompose.py`'s `CENSUS_SUCCESS` and both
  carry a non-empty reason, so this arm is an *explained* absence in both
  vocabularies. `coverage.missing_unexplained` is zero either way, and
  `gates/p2.sh`'s zero-`MISSING-UNEXPLAINED` requirement is met by the shipped
  census as it stands.
- **What does differ** is the `coverage.by_status` bucket the arm lands in
  (`unrunnable` here, `alias_duplicate` in every later pass) and the mechanism the
  reason text claims. A reader comparing this pass's census against a P3 pass's
  will see one arm move between buckets; that move is this note, and nothing else.
- **Do not read the shipped reason as evidence about `force_coretype()`.** It is
  the one substantive falsehood in this dataset's provenance, and correcting it is
  the reason this file exists.

## Why this was not re-run

Re-running the pass to regenerate one reason string on a zero-record arm costs a
fresh on-demand `c8g.metal-48xl` sweep (~10 instance-hours, ~$80) and changes no
measurement. Decided with Scott 2026-08-20: document the discrepancy instead.
