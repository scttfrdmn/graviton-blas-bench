# Dataset note — superseded census reason on the `NEOVERSEN2` arm

**Applies to:** run `20260820T031023Z-ip-172-31-36-19`
(`c8g.metal-48xl`, `i-04194f1208ee1d602`, `us-east-1a`, on-demand, P2 pass 1)
**File affected:** `census-20260820T031023Z-ip-172-31-36-19.ndjson`, one record
**Records affected in `bench-*.ndjson`:** none
**Written:** 2026-08-20, while the pass was still running
**Harness at time of run:** `9048a2b` — which is *before* `fda125b`

This note exists because the census of this pass carries a status and a reason
string that the current code can no longer emit for this arm, and a published
record containing an unreachable status is defensible only if the discrepancy is
documented. It is not an erratum against a measurement: no number in this dataset
changes, and no arm that ran is affected. It is an erratum against one
*explanation of an absence*.

The shipped census is **not** edited. Editing a record after it shipped is worse
than either leaving the discrepancy or re-running, because it destroys the only
evidence of what the harness actually did.

## What the record says

```json
{
  "record": "arm_outcome",
  "library": "openblas", "target": "DYNAMIC", "coretype": "NEOVERSEN2",
  "coretype_effective": "neoversev2", "threads": 0,
  "status": "unrunnable", "records": 0,
  "reason": "requested coretype NEOVERSEN2 but openblas_get_corename() reports
             neoversev2, which is not a declared alias of it; force_coretype()
```

## What it should say, and does say from `fda125b` onward

```json
{
  "record": "arm_outcome",
  "library": "openblas", "target": "DYNAMIC", "coretype": "NEOVERSEN2",
  "coretype_effective": "neoversev2", "threads": 0,
  "status": "alias_duplicate", "records": 0,
  "reason": "requested NEOVERSEN2; openblas_get_corename() reports 'neoversev2',
             which the NEOVERSEV2 arm is already measuring. The two requests
             select the same kernel set -- that is the finding, and measuring it
             twice would read as two independent arms."
}
```

Same arm, same `threads=0`, same `records=0`, same single record emitted from the
same pre-flight coretype probe loop in `scripts/run-matrix.sh`. Only the status
and the reason differ.

## Why the shipped reason is wrong, not merely differently worded

The shipped reason asserts that `force_coretype()` ignored the request. It did
not. In OpenBLAS `cc3fc1e` (the SHA this pass built, recorded in
`manifest-*.ndjson`), the identity holds at three independent levels:

- **The build system.** `kernel/arm64/KERNEL.NEOVERSEV2` is one line, 39 bytes:
  `include $(KERNELDIR)/KERNEL.NEOVERSEN2`. There is no V2 kernel table. The two
  names select a byte-identical set of kernels *by construction*, before any
  runtime dispatch is involved.
- **The C.** `driver/others/dynamic_arm64.c` `#define`s `gotoblas_NEOVERSEV2` to
  `gotoblas_NEOVERSEN2` unconditionally — outside every `DYN_*`/`NO_SVE` branch,
  with no `extern` for a V2 table anywhere. The two names are one pointer.
- **The read-back.** `force_coretype("NEOVERSEN2")` matches `corename[13]`, finds
  it, and returns **exactly the table that was requested** — the request *was*
  honoured. `gotoblas_corename()` then tests `corename[12]` (`"neoversev2"`)
  *before* `corename[13]` (`"neoversen2"`) against that one pointer, so in this
  tree it can never return `"neoversen2"` for any request. Both requests report
  `neoversev2`.

**So `alias_duplicate` is not a charitable reclassification of a failed arm; it is
the correct description of a genuinely redundant one.** The makefile fact is what
makes that a statement about kernels rather than about labels: running the
`NEOVERSEN2` request would have re-measured a byte-identical kernel table under a
second name, and reported it as an independent arm. Nothing was lost by declining
it, and nothing would have been gained by running it. The reported name differing
from the requested name is the campaign's central aliasing assumption coming true
on SVE2 silicon — the *finding*, not a failure. The `9048a2b` alias guard declared
only the `NEOVERSEV2:neoversen2` direction and this hardware takes the other one,
so the check meant to *detect* the aliasing is what suppressed it. `fda125b`
declares both directions; `9667ea0` is its follow-on and unrelated.

## A known limit this exposes, for P3

Standing order 10 says an arm is labelled with what the library *reported*, never
with what was requested, and `gbb-coreprobe`'s read-back is the mechanism. On the
`NEOVERSEN2`/`NEOVERSEV2` pair that mechanism is **blind**: both requests report
`neoversev2`, so read-back cannot tell which of the two tables was selected.

It is blind harmlessly, and only because of the makefile fact above — there is only
one table, so there is nothing for it to fail to distinguish. Recorded here rather
than left to be found later, because the *reasoning* is what makes it harmless. If
a future OpenBLAS gives V2 a kernel table of its own, or reorders `corename[]`, the
read-back becomes load-bearing on this pair overnight and the alias declaration in
`alias_ok()` becomes wrong in the dangerous direction — a request silently landing
on a different table than the label claims, which is standing order 10's
"plausible wrong answer". Re-derive it against the pinned SHA, do not assume it.

## What this does and does not change in the analysis

- **The measured arm set is identical, and complete.** `NEOVERSEN2` produced zero
  bench records under either status, on purpose and for the same underlying reason,
  so every GFLOP/s, efficiency figure, verdict and denominator in this dataset is
  unaffected. Because `KERNEL.NEOVERSEV2` *is* `KERNEL.NEOVERSEN2`, no kernel set
  went unmeasured either: the surviving `NEOVERSEV2` arm measured it.
- **Standing order 11 is satisfied either way.** `unrunnable` and
  `alias_duplicate` both sit outside `decompose.py`'s `CENSUS_SUCCESS` and both
  carry a non-empty reason, so this arm is an *explained* absence in both
  vocabularies. `coverage.missing_unexplained` is zero either way, and
  `gates/p2.sh`'s zero-`MISSING-UNEXPLAINED` requirement is met by the shipped
  census as it stands.
- **What does differ** is the `coverage.by_status` bucket the arm lands in
  (`unrunnable` here, `alias_duplicate` in every later pass) and the mechanism the
  reason text claims. A reader comparing this pass's census against a P3 pass's
  will see one arm move between buckets; that move is this note, and nothing else.
- **Do not read the shipped reason as evidence about `force_coretype()`.** It is
  the one substantive falsehood in this dataset's provenance, and correcting it is
  the reason this file exists.

## Why this was not re-run

Re-running the pass to regenerate one reason string on a zero-record arm costs a
fresh on-demand `c8g.metal-48xl` sweep and changes no measurement. Decided with
Scott 2026-08-20: document the discrepancy instead. (The estimate quoted when that
decision was taken, ~10 instance-hours and ~$80, was later measured at 5.5–7.7 h and
$42–59 — see issue #3. It does not change the decision, and the smaller number is
recorded here rather than the one that was quoted, because the quoted one is wrong.)
